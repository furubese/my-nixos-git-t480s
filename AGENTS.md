# AGENTS.md

This file gives any AI agent (human-directed or automated, e.g. a future `ai-issue-handler.yml`)
the guardrails needed to safely edit this repository. Read this before making changes.

## What this repo is

A flake-parts + Home Manager + sops-nix NixOS configuration for a single host, `t480s`
(a real, physical AMD-based ThinkPad T480s). See `story.md` for the original architecture
sketch and `docs/article-log.md` for the decision history (this repo doubles as the source
material for a written article about building it — see "Article log" below).

## Edit boundaries (read this first)

- **`modules/packages.nix`** is the intended surface for routine, human-authored package
  additions. Keep it to a plain `environment.systemPackages` list; don't grow logic into it.
- **`modules/ai/**`, `home/ai/**`, `tests/ai/**`** (direct children only, no subdirectories,
  never `default.nix`) are the AI-driven Issue→PR pipeline's edit scope — see "AI駆動の
  Issue→PR自動化" below. `modules/ai/default.nix` and `home/ai/default.nix` auto-import every
  `.nix` file placed directly inside their own directory; this is a deliberately narrow,
  opt-in subdirectory rather than an auto-import of all of `modules/**`, because the latter
  would also auto-import `modules/overlays.nix` (an overlay *function*, not a NixOS module)
  and break evaluation — a real bug caught during the v1→v2 consensus review of the redesign
  that added these directories. **This allow-list is a path restriction, not a capability
  sandbox**: a file inside `modules/ai/` can still set arbitrary NixOS options (that's the
  point — the AI writes real Nix code, not just package names). The actual defense is
  `.github/scripts/ai_pipeline.py`'s mechanical path/scope checks plus mandatory human review
  of the full diff before merge.
- **`hosts/t480s/hardware-configuration.nix`** — never hand-edit. Its own header says so:
  it's machine-generated by `nixos-generate-config` and must be regenerated on the real
  machine if hardware changes, not patched by hand or by an agent.
- **`hosts/t480s/configuration.nix`** — real host config. Structural changes here (bootloader,
  filesystems, hostname) are high-blast-radius; treat with more caution than `modules/*.nix`.
  The only changes it should carry beyond what NixOS's installer generated are the `imports`
  list, `networking.hostName`, and `nix.settings.experimental-features` — anything else
  probably belongs in a `modules/*.nix` file instead.
- **`flake.nix`** — the flake-parts skeleton was deliberately kept to one file with no
  third-party `flakeModules`, specifically so its blast radius stays legible. Don't add
  flake-parts modules/plugins without a real need; a plain `perSystem`/`flake` structure here
  was chosen after 3 rounds of review to keep evaluation errors easy to diagnose on a machine
  with no local Nix debugging aids other than the error message itself.
- **`secrets/`** — `secrets/secrets.yaml.example` is a plaintext template, never a real
  secrets file. Do not add `sops.secrets` or `sops.defaultSopsFile` anywhere in this repo
  unless a real age key has actually been generated and `secrets/secrets.yaml` has actually
  been encrypted with `sops` — an unconditional reference to a file that doesn't exist yet
  breaks evaluation for everyone, not just the person adding the secret.

## Version control

- Use **GitButler (`but`)** for all commits/branches/PRs in this repo, not raw `git`. See the
  `gitbutler` skill for command recipes if you're a Claude Code agent.
- One feature/change per branch; don't bundle unrelated changes into one commit.
- Never rewrite the `main`/`gitbutler/workspace` history without being asked.

## CI

- `check-light.yml` runs on PRs touching `hosts/**`, `modules/**`, `flake.nix`, `flake.lock`,
  `home/**`, or `tests/**`. If you add a new top-level directory that affects the build,
  add it to that `paths` filter — don't rely on people noticing CI didn't run.
- `check-desktop.yml` is **`workflow_dispatch` only, on purpose** — `modules/desktop.nix` is
  currently an unimported stub, so a `pull_request` trigger on it would be a guaranteed-red
  check on a public repo. Only add a `pull_request` trigger back once `modules/desktop.nix`
  is a real, working module that's actually imported.
- **AI pipeline overview (v2, free-form Nix generation)**: three workflows —
  `ai-issue-handler.yml`, `ai-issue-autofix.yml`, `ai-issue-feedback.yml` — share one design.
  The AI (OpenRouter, `z-ai/glm-5.3`, not the Claude Code CLI — deliberate, don't "helpfully"
  switch it back) is allowed to generate real Nix code, but only as a JSON object
  `{"files": {"<path>": "<full content>", ...}, "title": "...", "summary": "..."}` whose keys
  must all pass `.github/scripts/ai_pipeline.py`'s path allow-list
  (`modules/ai/**`, `home/ai/**`, `tests/ai/**`, direct children only, never `default.nix`).
  That script is always checked out from `main` (`path: _trusted`) — an AI-controlled branch
  can never rewrite the rules that constrain it. After writing files, every workflow: (1) runs
  `git add -A` then diffs `git diff --cached --name-only` against the AI's own declared file
  list and fails closed on any mismatch (`git diff --name-only` alone misses new/untracked
  files — a real bug from an earlier draft); (2) runs `nix-instantiate --parse` on every
  changed `.nix` file (syntax only — real build verification is `check-light.yml`'s job, not
  duplicated here); (3) runs an **advisory-only** content scan for dangerous constructs
  (`hashedPassword`, `systemd.services`, `lib.mkForce`, etc.) that never blocks a PR, only adds
  a `needs-careful-review` label (regex scanning is trivially bypassed by nesting attrsets, so
  it can't be a real gate — human full-diff review before merge is the actual defense). All
  three workflows are gated on the `vars.AI_PIPELINE_ENABLED` repo variable
  (`gh variable set AI_PIPELINE_ENABLED --body true` to turn the pipeline on — unset means
  fail-closed) and share one GitButler-style concurrency key per issue,
  `ai-branch-ai/issue-N`, so the three workflows never race each other on the same branch.
- `.github/workflows/ai-issue-handler.yml` runs on `issues: labeled` and is gated on the
  `package-request` label (adding a label requires triage/write repo access, which is what
  keeps a public repo's issue tracker from being an open trigger). It force-resets
  `ai/issue-N` from `main` every run, writes the AI's declared files, and opens (or updates) a
  PR with an AI-generated title/summary instead of the old fixed `packages: address #N` title.
  Issue title/body are untrusted input, sanitized via `ai_pipeline.sanitize_text` (strips HTML
  comments, including unclosed ones — a plausible prompt-injection vector) and passed via
  `env:`, never interpolated directly into a `run:` shell block.
- `.github/workflows/ai-issue-autofix.yml` is dispatched directly by `check-light.yml`'s
  `dispatch-autofix` job on its own build failure (`workflow_dispatch` with `branch`/`run_id`
  inputs) — **not** a `workflow_run` chain. An earlier draft relied on `workflow_run`, and a
  Critic review during the redesign found it empirically never fired (0-for-4 in real runs)
  because of how `GITHUB_TOKEN`-authored PRs gate their first workflow run; direct dispatch
  from check-light's own failure handler was adopted instead. Both `branch` and `run_id` are
  untrusted `workflow_dispatch` inputs and are validated via
  `ai_pipeline.py validate-dispatch` (branch regex, matching same-repo bot-authored PR, run_id
  attribution) **before** the branch is ever checked out. Because `_trusted/` (checked out from
  `main` for that validation) gets deleted by the later branch checkout (`actions/checkout`
  clears a target directory lacking a matching `.git`), it's copied to `$RUNNER_TEMP` first —
  this exact checkout-ordering bug was caught and fixed in an extra post-consensus Architect
  review, so don't reorder these steps without re-verifying that interaction. It does **not**
  distinguish "AI wrote broken Nix" from "unrelated CI flake" (deliberate simplicity choice).
  Attempt count is derived from commits carrying an `AI-Autofix-Attempt: true` trailer on
  `origin/main..HEAD` (no external state store); cap is 3 attempts, after which it comments on
  the PR and stops.
- `.github/workflows/ai-issue-feedback.yml` reacts to `issue_comment` on a PR, but only when
  the commenter is `github.repository_owner` and the `resolve` job confirms the PR is a
  same-repo, bot-authored `ai/issue-N` PR. After pushing a fix commit, it does **not** post a
  reply comment — that was an explicit Deep Interview decision (Round 10) — with one
  consented exception: if the advisory content scan flags something, it both labels and
  comments on the PR to make sure the extra-review signal isn't silently missed.
- All three AI workflows dispatch `check-light.yml` (`gh workflow run check-light.yml --ref
  <branch>`) after pushing, rather than relying on it auto-triggering on the push: a PR's
  *first* workflow run under `GITHUB_TOKEN` authorship requires manual "Approve and run" in the
  GitHub UI, but `workflow_dispatch` is an explicit exception to that gate, so this is how the
  AI-authored branches get a CI run without a human clicking approve first.
  `check-light.yml` itself is `pull_request` + `workflow_dispatch` triggered, `contents: read`
  only, and skips passing a Cachix `authToken` (rather than skipping the whole Cachix step) on
  `ai/issue-*` branches (matched via `github.head_ref || github.ref_name`, since `ref_name`
  alone means something different under `pull_request` vs. other triggers), so AI-generated
  build artifacts are never pushed to the cache, only read from it. Its `dispatch-autofix` job
  is split out from `build` specifically so only that one job needs `actions: write`.

## Testing without a local Nix install

Some environments this repo gets edited from (e.g. a Fedora dev machine) don't have `nix`
installed. When that's the case, don't skip verification — substitute mechanical checks:
- every relative path referenced in `.nix` files actually resolves (`test -e`)
- every `.#checks.<system>.<name>` / `.#nixosConfigurations.<name>` referenced in a workflow
  YAML (outside comments) has a matching definition in `flake.nix`
- no bare (unprefixed) reference to an input name (e.g. `nixpkgs.`, `home-manager.`) outside
  the `inputs = { ... }` block or a `let ... = import inputs.<name> ...` binding
- `grep -rnE 'AGE-SECRET-KEY-1|-----BEGIN [A-Z ]*PRIVATE KEY-----|age1[a-z0-9]{58}'` across the
  repo returns zero hits (the `.sops.yaml` placeholder is deliberately shaped to not match)

Real `nix flake check` / `nixos-rebuild test` still has to happen on a Nix-capable machine
(ideally the actual `t480s`) before merging anything non-trivial — don't claim something
"works" based on the mechanical checks alone.

## Article log

`docs/article-log.md` is intentionally kept in this public repo (unlike `.omc/**`, which is
gitignored and never enters history). When you make a non-trivial decision — not just "what"
but "why", and what alternative was rejected and why — add a short, rationale-focused entry.
Don't paste full command output or file contents into it; that belongs in the commit itself.
